# marth's Jukebox — design (draft 1, 2026-10-27)

SKSE plugin that replaces Skyrim's music with tracks served by a Harmony server
(`marthofdoom/harmony`, `docs/api/game-source.md`). The player picks a genre / artist / playlist /
query for each Skyrim music environment.

## 1. What the Harmony API gives us (verified against docs/api/game-source.md)

- `PUT /api/game/profiles/{name}`: `types` maps a music-type name to a selector
  (`genre | query | playlist | album | artist`, or a list = union). A `default` type is the fallback.
- `POST /api/game/next {profile,type,count,peek}`: bag-shuffled picks, returns `audio_url`.
- `GET /api/game/audio/{svc}/{id}.wav`: canonical 44-byte-header PCM WAV, `202` + `Retry-After` while
  transcoding, Range/HEAD supported, ETag.
- `POST /api/game/playing`: now-playing report. `GET /api/game/status`: ffmpeg/cache/enabled check.
- Auth: optional `X-Harmony-Key` header. No accounts needed (YT Music public catalogue by default).
- The doc already prescribes the **double-slot file pattern** for engines that play from disk.

## 2. How Skyrim plays music (CommonLib mit-3.7 fork headers)

- `BGSMusicType` (MUSC) -> `BSIMusicType::tracks` (`BSTArray<BSIMusicTrack*>`, +0x30)
  -> `BGSMusicTrackFormWrapper` (MUST, `track` @+0x30) -> `BGSMusicSingleTrack` (`trackID` @+0x20 = hashed
  path of the .xwm/.wav) | `BGSMusicPaletteTrack` (layered) | `BGSMusicSilenceTrack`.
- `BSMusicManager::GetSingleton()` (`RELOCATION_ID(514738,400896)`): `musicQueue`, `current`
  (the BSIMusicType now playing). `BSIMusicType::typeStatus`, `currentTrackIndex` are readable.
- Skyrim.esm: **50 MUSC, 258 MUST** (EDIDs enumerated; list in section 4).
- The engine streams the track from a file, so a file being played must not be overwritten.

## 3. Proposed architecture

**Runtime retarget, not ESP overrides.** An override ESP of MUSC records fights every music mod in a
modlist (Requiem, LoreRim...). Instead the plugin edits the winning in-memory MUSC at `kDataLoaded`.

1. **Tiny ESL-flagged ESP** (generated by a script, like `MFO_GenerateESP.py`): two MUST records per
   category, `MJ_<cat>_A` / `MJ_<cat>_B`, each a single track with ANAM `Music\Harmony\<cat>_a.wav` /
   `_b.wav`. The engine builds the track objects for us; we create no forms at runtime.
2. **Retarget at kDataLoaded**: for each enabled category, the MUSC's `tracks` array is shrunk/overwritten
   in place to `[A, B]` (never reallocated; originals stashed in our own vector so we can restore). Needs
   `kCycleTracks` so the engine alternates A/B. A category the player left on "Vanilla" is untouched.
   Open question: a source MUSC with exactly 1 track cannot grow to 2 without allocator work; the
   fallback is pointing `wrapper->track` between two prebuilt single tracks (decide at spike time).
3. **Pool of 3 per type (marth 2026-10-27)**: the plugin keeps 3 downloaded tracks ready for every
   enabled type, in its own cache dir (not the engine's). When a type's music event fires, one of the
   3 is picked at random (local shuffle), renamed into the idle engine slot (same filesystem, so cheap),
   and played; a worker then asks `next` for a replacement and downloads it in the background, so the pool
   is back to 3 for the next event. Only the played track is replaced: a track that never played stays
   in the pool (marth 2026-10-27), also across game sessions, so the pool is persisted on disk and
   revalidated at load (file present, size matches the recorded Content-Length). Pools are prefilled at game load, enabled types only
   (combat first: it gives no warning). **`normalize=1` is always on (marth)**; the 29 s cold cost is
   hidden by the pool, since downloads never block playback.
   Detection is a read-only poll (SKSE task, ~250 ms) of `BSMusicManager::current` +
   `typeStatus`/`currentTrackIndex`; slot writes use `.tmp` -> verify Content-Length -> rename; the
   plugin reports `playing`. No engine hooks in v1 (lowest crash surface first, MFO BUILD.md ordering).
   Disk: ~25 MB/track x (3 pool + 2 slots) x ~12 types = ~1.5 GB worst case; the cache dir gets an LRU
   cap setting.
   Measured on harmony:8080 (2026-10-27): cold+normalize 29 s, cold 6.9 s, cached 0.6 s.
4. **Never silence the game**: if Harmony is unreachable or the slot is not ready, restore the original
   `tracks` for that MUSC before its next play and log it loudly (a documented degrade, not a mask).
5. **Network = WinHTTP** (no extra deps, works under Wine/Proton, https for free).
6. **Settings UI**: MCM Helper / INI for v1 (server URL, key, per-category source). A profile is pushed
   to Harmony with `PUT` from the plugin's defaults; a genre/artist picker needs the server's
   `/api/search` (not yet documented) — likely a v2 in-game menu, or v1 = pick in Harmony's own UI.

## 4. Category grouping (50 vanilla MUSC -> ~12 player-facing types)

explore (Tundra/Mountain/Snow/Marsh/Coast/Reach/ForestPine/ForestFall/Generic), town/city (Castle,
Discovery*), tavern (Tavern, TavernB), dungeon (Dungeon, Cave, Fort, Ice, Dread), combat (Combat,
CivilWar), boss (CombatBoss, Alduin/Odahviing), discovery/stinger, special (WordOfPower, Reveal, Success,
Death, Reward, Elder Scroll, Cart, Intro), skills menu, Sovngarde (Chant/Hall of Valor), dungeon cleared.
Each group = one Harmony `type`; the plugin maps MUSC EDID -> group, so unknown MUSC from other mods fall
into `default`.

## 5. Known risks (each needs a field probe, "disassembly proves a path exists, not that it runs")

- Does the engine accept a loose **.wav** as a music ANAM, at 48 kHz/16-bit stereo? (Fallback: ffmpeg to xwm
  is not available on a player's machine; the server can already emit 44.1 kHz.)
- Does the engine open/prefetch the next track early (would break the "write the idle slot" rule)?
- Is a loose file locked under Wine while playing (it decides whether single-slot rename would even work)?
- Does in-place `tracks` mutation survive save/load and MUSC reuse by cell/location records?
- Cold download latency (5-15 s for streaming tracks) vs. short combat music: the prefetch must run
  *before* a type is needed; combat has no warning. Mitigation: keep a pre-fetched track per hot type.
- The engine is single-instance for ANAM hash: `BSResource::ID` is computed at record load, so the path of
  a slot is fixed by the ESP, which is the reason for the fixed slot filenames.

## 6. Nexus rules (File Submission Guidelines, help.nexusmods.com/article/28)

- Executables that connect to the internet are **prohibited unless crucial to the mod** — ours is crucial,
  but it should be flagged: contact staff before upload, offer the source, and make the mod page say
  plainly what it connects to (user-configured Harmony server only; no telemetry, no auto-update).
- No copyrighted content without permission: the mod ships **no audio**; all audio comes from the user's own
  library/streaming accounts via their own server. The page must state requirements (a running Harmony
  server) clearly. No links to external sources for impermissible files, so the page should link the Harmony
  repo only as software, not as a music source.
- Disclose any AI-generated code per the AI tagging rule. Credit CommonLibSSE-NG (MIT fork).
- Not a "registration" problem: no account is needed to use the mod.

## 7. Process (from MFO CLAUDE.md, adopted)

- Sonnet writes code against precise specs; Opus authors tier-A (hooks, ABI, threading, TU splits) and
  reviews every diff; Fable only for escalation.
- Verify every symbol in `_commonlib/mit-3.7-fork` (not `live-alandtse-ng`). Subsystem folders under
  `native/`, ~1500-line split rule, one mechanism per build, CI is the only compiler (no local MSVC), and
  a green CI on your own SHA before reporting success. Registry: `marthofdoom/vcpkg-registry`.
- Milestones: M0 spike (retarget one MUSC + one WAV slot, hardcoded file) -> M1 prefetch/slot loop ->
  M2 per-category profile + INI -> M3 fallback/restore + logging -> M4 in-game picker -> release.
