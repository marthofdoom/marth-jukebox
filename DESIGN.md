# marth's Jukebox — design (draft 1, 2026-10-27)

SKSE plugin that replaces Skyrim's music with tracks served by a Harmony server
(`marthofdoom/harmony`, `docs/api/game-source.md`). The player picks a genre / artist / playlist /
query for each Skyrim music environment.

## 1. What the Harmony API gives us (verified against docs/api/game-source.md)

- `PUT /api/game/profiles/{name}`: `types` maps a music-type name to a selector
  (`genre | query | playlist | album | artist`, or a list = union). A `default` type is the fallback.
- `POST /api/game/next {profile,type,count,peek}`: bag-shuffled picks, returns `audio_url`.
- `GET /api/game/audio/{svc}/{id}.wav`: canonical 44-byte-header PCM WAV, `202` + `Retry-After` while
  transcoding, Range/HEAD supported, ETag.
- `POST /api/game/playing`: now-playing report. `GET /api/game/status`: ffmpeg/cache/enabled check.
- Auth: optional `X-Harmony-Key` header. No accounts needed (YT Music public catalogue by default).
- The doc already prescribes the **double-slot file pattern** for engines that play from disk.

## 2. How Skyrim plays music (CommonLib mit-3.7 fork headers)

- `BGSMusicType` (MUSC) -> `BSIMusicType::tracks` (`BSTArray<BSIMusicTrack*>`, +0x30)
  -> `BGSMusicTrackFormWrapper` (MUST, `track` @+0x30) -> `BGSMusicSingleTrack` (`trackID` @+0x20 = hashed
  path of the .xwm/.wav) | `BGSMusicPaletteTrack` (layered) | `BGSMusicSilenceTrack`.
- `BSMusicManager::GetSingleton()` (`RELOCATION_ID(514738,400896)`): `musicQueue`, `current`
  (the BSIMusicType now playing). `BSIMusicType::typeStatus`, `currentTrackIndex` are readable.
- Skyrim.esm: **50 MUSC, 258 MUST** (EDIDs enumerated; list in section 4).
- The engine streams the track from a file, so a file being played must not be overwritten.

## 3. Architecture (as built for 1.0, branch core-playback; spec docs/INTEGRATION-1.0.md)

**Runtime retarget, not ESP overrides.** An override ESP of MUSC records fights every music mod in a
modlist (Requiem, LoreRim...). Instead the plugin edits the winning in-memory MUSC, in place.

0. **Slot files exist before the game starts** (Steam Deck field log 2026-10-27): slot files the plugin created DURING a
   session were never played (the engine started each pick and skipped it at once: a new sound handle and a new
   entry every 250 ms tick), while the M0b/M0c slot files, present at game start, played and could be renamed over.
   So at plugin load (before the engine initialises) every missing `slot_NN.wav` is created as 1 s of silence, and every
   real fill is a rename over an existing file. The likely mechanism (the engine resolving a music file's hashed
   `BSResource::ID` against what it found when it started) is inferred from this evidence, not from the binary. A flood
   guard backs it: 6 play events of one slot within 5 s = the engine cannot play that file -> one loud error, the
   environment goes back to vanilla (when its type is idle) and the slot is not refilled until the settings change or
   the game restarts. Each of the first 5 play events per slot also gets a "+500 ms" check line in the log.
   **Field #4 (Deck): a fight never waits on the network.** A dry pool now refills its slot from the environment's
   recently played cached tracks whether or not the type plays (a replay counts as ready, so the type is not restored to
   vanilla while the cache can play); combat and boss keep at least 5 tracks ready; urgent pools (empty, or combat/boss
   below 2) are refilled first and may cancel a running non-urgent download, which itself gets 60 s (not 180 s) for a cold
   transcode and is retried 3 min later. Profiles on Harmony 1.0.13+ set `trim_silence`, so tracks start without leading
   silence. Workers run below normal priority in background IO mode; slot files are written without a forced flush and
   paced (2 ms per 4 MiB); the stall detector's warning says what our workers were doing (`ours: ...`).
   **Field #5 (Deck):** a pool is urgent at one track left (that one is usually already in the slot), and the play that
   leaves it there cancels a running non-urgent download for another environment; a cold pick that misses the 60 s
   non-urgent deadline is retried directly 90 s later (no new `next` pick); the number of tracks kept ready adapts to the
   observed download time vs track length (`max(setting, ceil(download/track)+2)`, at most 8). PerfProbe: once a minute
   `[perf] game thread in our watcher task ...` (avg/max per tick, game-thread waits > 20 ms for the pool lock and who
   held it); `[stall]` lines say whether a loading screen was open.
1. **Slot wrappers.** `MarthJukebox.esp` (ESL, generated by `tools/make_esp.py`) holds K = 24 single-track
   MUST records `MJ_SLOT_00..23` (local ids 0x800..0x817), ANAM `Data\Music\Harmony\slot_NN.wav`. The engine
   builds the track objects; we create no forms at runtime. The mod ships no audio: the slot files are
   written by the plugin.
2. **One slot per active environment** (`native/retarget/`). Every music type is classified
   (`categories/`); a type whose effective environment (a Settings group, or a group.sub that has its own
   section) is active gets that environment's slot. Assignment is deterministic (`AssignSlots`: an
   environment keeps its slot across settings changes, newcomers take the lowest free slot in sorted order);
   more than 24 active environments: the extras stay Vanilla, logged. All Single/Palette entries of the type
   are pointed at the slot wrapper in place (array size never changed, Silent and other entries kept,
   originals saved per index), only from the 250 ms watcher task while the type is not current, not queued
   and Inactive/Finished (M0b rule). Diegetic, kept-vanilla, all-silent and unmapped types are never touched.
   The array is re-asserted if it grows later (M0b: entries are appended before the main menu).
3. **Pools** (`native/pool/`): per active environment a pool of N validated tracks (setting 3/5/8) in the
   cache dir, file name = FNV-1a 64 hash of (service, id) (never the raw id), recorded in `index.json`
   (service, id, title, artist, duration, bytes, sources, selector fingerprint). Persisted across sessions,
   revalidated at load (file present, size matches); a pool whose fingerprint (type name, mode, selector,
   service, id, `sources`) changed is dropped. Refill on the pool thread: `next` (count = max(3, missing),
   consumed) -> drop picks that are in the plugin's recent-played list (last 50 per environment, persisted)
   or already pooled -> download (FLAC when `status.containers` has it and `[Features] Flac=1`, else WAV) ->
   full decode check + preview guard (decoded duration >= 90% of `duration_s` when > 60 s, DESIGN 8.8) -> pool.
   Only the PLAYED track leaves the pool. Empty pools and combat/boss fill first. LRU cap `CacheCapMB` over the
   cache, never evicting pooled or slotted files. Back-off: 2 s doubling to 5 min after timeouts/unreachable;
   `no_tracks` = 10 min and the environment stays Vanilla with a plain-language reason.
   `sources`: `library` by default; streaming checkbox = `library,ytmusic` (+`,qobuz` only with
   `[General] AllowQobuz=1`); a Harmony older than 1.0.13 (no `services` in `status`, so no source list) can
   only stream through `all`, which may include Qobuz, so it is used only with AllowQobuz=1, else the
   environment plays from the library and says so.
4. **Slot fill = the M0c protocol** (slot thread). Each slot file holds its environment's next unplayed pool
   track (prefilled before the first play). A play event (the slot wrapper's sound handle or the index changed
   while its type is current; a resume after combat keeps both and is not an event) marks the placed track as
   served (out of the pool, into the recent list, `POST /api/game/playing`), and once the play has been stable
   1.5 s the next pool track is decoded/copied to `slot_NN.wav.tmp` as a canonical 44-byte-header PCM WAV
   (dr_flac for FLAC), flushed, size-checked and `MoveFileExW(REPLACE_EXISTING)`-ed over the playing file. The
   plugin never overwrites a slot file it did not write (sizes recorded in
   `Data\SKSE\Plugins\MarthJukebox\slots.json`), and never writes a slot for one environment while another
   environment's types still point at it.
   **Never silence the game**: a type is pointed at its slot only while the slot holds an unplayed track of its
   environment (or for 10 s after a play while the refill is due); otherwise its original tracks are restored
   (when safe) and that is logged loudly. **Pool dry while the type is playing** (Harmony down, or a refill not in
   yet): the slot is refilled with the environment's recently played tracks that are still in the cache, least
   recently played first, so the player hears a rotation of earlier tracks instead of the same song in a loop; only
   if none is cached does the last track repeat (logged). As soon as the type stops, the vanilla tracks come back.
   A rename that fails (Windows sharing violation) keeps the prepared `.tmp` and retries only the rename (2, 5, 15,
   then 60 s, and only while that slot is not the one playing; access-denied gives up after 3 tries, loudly).
   While at least one environment plays from Harmony and the server stays unreachable, an in-game notification says
   so (`[General] ToastEnabled`, every `ToastIntervalMinutes`, default 5; one "Harmony is back" on recovery).
   **The one new engine call of 1.0** is that notification: `RE::DebugNotification` (`RELOCATION_ID(52050, 52933)`,
   fork `include/RE/M/Misc.h`), called only from the 250 ms watcher task on the game thread, never over the main menu or
   a loading screen. It is shipped by MFO but NOT yet field-proven in this plugin until the toast is seen in game; its
   kill switch is `ToastEnabled=0`.
   Remember-place ON is the engine's own resume (M0b); OFF has no safe
   read-only mechanism yet, so 1.0 stores the setting and behaves as ON.
   Threads: game thread = probe + retarget only; pool thread = settings load, Harmony, pools, cache; slot thread
   = slot files; UI thread (app/) = connection test, search, preview, now-playing reports. Kill switches:
   `[Features] Retarget/Network/Flac`, the file `Data\SKSE\Plugins\MarthJukebox.noretarget` (restores
   everything when it appears), no ServerUrl = everything Vanilla and no network.
   Measured on the test server (2026-10-27): cold+normalize 29 s, cold 6.9 s, cached 0.6 s: hidden by the pool.
5. **Network = WinHTTP** (no extra deps, works under Wine/Proton, https for free).
6. **Settings UI (marth 2026-10-27: an SKSE menu)**: an ImGui page registered with the SKSE Menu
   Framework (Nexus SSE; a shared window that mods register pages with; hard requirement, to be
   verified for 1.5.97/1.6.1170 and its API license before adoption), not MCM, because MCM has no text
   fields or dynamic search lists. Page: server URL, key (masked), test-connection button, per category a
   source picker (Vanilla / Genre / Artist / Playlist / Query) with a search box backed by `/api/search`,
   a per-category **"Allow streaming (YouTube Music)" checkbox**, off by default
   (marth 2026-10-27), cache cap, pool status. The checkbox maps to the request-level `sources` field
   of `POST /api/game/next` (`library` unchecked, `library,ytmusic` checked; Qobuz only via the INI, 8.8), so
   it is decided per type with no profile rewrite; the pool fingerprint includes `sources`, so flipping the
   box drops that type's pool.
   Default is library only, see docs/NEXUS-COMPLIANCE.md.
   Settings persist to an INI in `Data/SKSE/Plugins/`; the plugin `PUT`s the resulting profile to
   Harmony. Fallback if the framework proves unsuitable: own ImGui overlay as in MFO's Board (more
   code; it duplicates the framework's D3D/UI hooks, so the two must be mutually exclusive).
   Research result (docs/MENU-FRAMEWORK.md, 2026-10-27): ADOPT. Two calls register a page
   (`SetSection` + `AddSectionItem(name, cb)`, namespace `ImGuiMCP::`); the vendored header (LGPL-2.1)
   wraps ImGui 1.90.8 so we never link imgui; the DLL is All Rights Reserved: list it as a REQUIREMENT,
   never bundle it. Also needs ImGui Icons (Nexus 114790) and Address Library. The framework has no
   settings persistence or hotkey API: we keep our own INI. The render callback runs on the UI thread:
   it may only read atomics/copies. Correction: MFO does NOT use the framework (its Board is its own
   ImGui overlay); it is Harbinger that does. Open (in-game tests): the cached-null-pointer risk because
   our plugin sorts before "SKSE..." (log GetMenuFrameworkVersion() right after registering), 1.6.1170
   compatibility of the installed 3.14.0 (it is a CommonLibSSE-NG build), whether our 250 ms poll and the
   music keep running while the panel freezes the game, Ctrl+V paste into the masked key field, no
   gamepad text entry (so the key/URL need a keyboard; everything else must work on a controller).

## 4. Category grouping (50 vanilla MUSC -> ~12 player-facing types)

explore (Tundra/Mountain/Snow/Marsh/Coast/Reach/ForestPine/ForestFall/Generic), town/city (Castle,
Discovery*), tavern (Tavern, TavernB), dungeon (Dungeon, Cave, Fort, Ice, Dread), combat (Combat,
CivilWar), boss (CombatBoss, Alduin/Odahviing), discovery/stinger, special (WordOfPower, Reveal, Success,
Death, Reward, Elder Scroll, Cart, Intro), skills menu, Sovngarde (Chant/Hall of Valor), dungeon cleared.
Each group = one Harmony `type`; the plugin maps MUSC EDID -> group, so unknown MUSC from other mods fall
into `default`.

## 5. Known risks (each needs a field probe, "disassembly proves a path exists, not that it runs")

Status for 1.0 (docs/M0B-RESULTS.md, docs/M0C-RESULTS.md): a loose 16-bit PCM WAV at the hashed ANAM path plays
(heard); the engine re-opens the file on every play and resumes the same handle after an interruption; a rename
over the PLAYING file works on Proton + MO2/USVFS (9/9). Still open: the same rename on native Windows (a
sharing violation is retried, never forced) and 48 kHz files in the field (Harmony serves the profile's 44.1 kHz).

- Does the engine accept a loose **.wav** as a music ANAM, at 48 kHz/16-bit stereo? (Fallback: ffmpeg to xwm
  is not available on a player's machine; the server can already emit 44.1 kHz.)
- Does the engine open/prefetch the next track early (would break the "write the idle slot" rule)?
- Is a loose file locked under Wine while playing (it decides whether single-slot rename would even work)?
- Does in-place `tracks` mutation survive save/load and MUSC reuse by cell/location records?
- Cold download latency (5-15 s for streaming tracks) vs. short combat music: the prefetch must run
  *before* a type is needed; combat has no warning. Mitigation: keep a pre-fetched track per hot type.
- The engine is single-instance for ANAM hash: `BSResource::ID` is computed at record load, so the path of
  a slot is fixed by the ESP, which is the reason for the fixed slot filenames.

## 6. Nexus rules (File Submission Guidelines, help.nexusmods.com/article/28)

- Executables that connect to the internet are **prohibited unless crucial to the mod** — ours is crucial,
  but it should be flagged: contact staff before upload, offer the source, and make the mod page say
  plainly what it connects to (user-configured Harmony server only; no telemetry, no auto-update).
- No copyrighted content without permission: the mod ships **no audio**; all audio comes from the user's own
  library/streaming accounts via their own server. The page must state requirements (a running Harmony
  server) clearly. No links to external sources for impermissible files, so the page should link the Harmony
  repo only as software, not as a music source.
- Disclose any AI-generated code per the AI tagging rule. Credit CommonLibSSE-NG (MIT fork).
- Not a "registration" problem: no account is needed to use the mod.

## 7. Process (from MFO CLAUDE.md, adopted)

- Sonnet writes code against precise specs; Opus authors tier-A (hooks, ABI, threading, TU splits) and
  reviews every diff; Fable only for escalation.
- Verify every symbol in `_commonlib/mit-3.7-fork` (not `live-alandtse-ng`). Subsystem folders under
  `native/`, ~1500-line split rule, one mechanism per build, CI is the only compiler (no local MSVC), and
  a green CI on your own SHA before reporting success. Registry: `marthofdoom/vcpkg-registry`.
- Milestones (revised, marth 2026-10-27: "Batch m1-m3 together"): M0a passive probe (done, merged) ->
  M0b retarget + slot-protocol spike (in review) -> **v0.1 = M1+M2+M3 as ONE build**: M1 Harmony client,
  pool of N, slot swap, fallback to vanilla; M2 SKSE Menu Framework page (guided, search, preview, per-
  environment toggles); M3 remember-place, FLAC, bigger pool. One LoreRim test cycle for the batch, then a
  GitHub release with the full README.
  How the batch stays bisectable (MFO "one hook class per build" still applies to ENGINE writes): v0.1
  adds NO new engine-write mechanism beyond M0b's in-place retarget; the new parts are network/file IO on
  a worker (M1, M3 decode), UI (M2), and a state file (remember-place). Build them as separate subsystem
  folders (`native/net/`, `native/pool/`, `native/menu/`) behind per-feature kill switches in the INI, so a
  crash bisects by switching a feature off. Order within the branch: net+pool, then menu, then FLAC and
  remember-place. The engine-dependent design (what happens when the engine re-picks a slot, crossfade,
  resume position) waits for the M0b log; the menu, the Harmony client and the Harmony-side FLAC change do not.

**8.7 Requirement: almost never the same track twice (marth 2026-10-27).** (As built: the recent list prefers unplayed
picks but never starves a small selection: when only recently played tracks come back, the least recently played is
taken and the menu says "Small selection: tracks will repeat"; a failed download is skipped for a while but never
counts as played. When Harmony is down and a pool runs dry during play, recently played cached tracks rotate, DESIGN
3 item 4. Deliberate since field #4: when a pool runs dry while the network is fine, the game repeats cached tracks of that
environment, even the only one, instead of falling back to vanilla.) A player who picks a genre should
essentially never hear a repeat. Two layers:
- **Harmony (branch `game-pools`)**: deeper streaming candidate lists (paging past 25 per query, a few query
  variants, mood/genre playlists where the provider allows), cross-service de-duplication, and a bag whose
  memory survives server restarts and unrelated profile edits. Measured 2026-10-27 on the live server:
  'folk' sources=all 228 candidates, 'ambient' 40, 'epic battle music orchestral' 56; caps today: streaming
  search 25 per service, library search 50, library genre 1000, artist 100, pool refresh 10 min.
- **Plugin**: keeps its own recent-played list (state file, per environment, bounded) and discards a
  server pick that is already in it, asking `next` again; the pool of N is filled only with tracks not
  recently played. The menu shows how many distinct tracks a selection can produce (pool size from
  `next`'s `pool_size`) and warns when it is small ("only 25 tracks: expect repeats").

**8.8 Qobuz is excluded; previews must never reach the game (marth 2026-10-27: no active Qobuz subscription).**
Measured on the live server: a Qobuz track with `duration_s` 224 produced a WAV of exactly 30.0 s (Qobuz
serves 30 s previews without a subscription). Consequences:
- The plugin's streaming checkbox means YouTube Music only. Harmony's `sources=all` still includes Qobuz when
  it is signed in, so v1.0 needs a Harmony change (follow-up branch after `game-pools`): `sources` also
  accepts a service list or an exclusion (for example `["library","ytmusic"]`), and `status` lists the usable
  sources.
- **Qobuz is opt-in via an INI switch (marth 2026-10-27):** `[General] AllowQobuz=0` by default. The per-environment
  streaming checkbox sends `sources` = `library,ytmusic`; only with `AllowQobuz=1` does it send
  `library,ytmusic,qobuz`. The key is never shown in the menu; the setting lives in the INI only. Harmony's
  `game-pools` branch accepts the service list (`sources` comma subset, `game_excluded_services`), so no Harmony
  exclusion is needed for this. Every `next` call passes `sources` explicitly (profile default is `library`).
- Independent of that, the plugin ALWAYS validates a downloaded track before it enters the pool: decoded
  duration (from the WAV `data` size, or FLAC STREAMINFO) must be at least 90% of the `duration_s` that `next`
  reported for tracks longer than 60 s; anything shorter is discarded, logged ("preview or truncated stream") and
  the pick is replaced. This also catches a cut-off network transfer and any other truncated source.
- Compression test results: docs/COMPRESSION-BENCH.md (FLAC L1 chosen; lz4 not useful on PCM).
